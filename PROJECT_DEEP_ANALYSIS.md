## 1. Project Overview

The **QR Code Attendance Scanner** is a Python desktop application designed for event management. It serves a **two-phase workflow**:

| Phase | Script | Purpose |
|---|---|---|
| **Pre-Event** | `email_ticket_sender.py` | Generate PDF tickets with QR codes and dispatch them via email |
| **At-Event** | `attendance_scanner.py` | Scan those QR codes using a webcam and record attendance |

The system is entirely **GUI-driven** using Python's built-in `tkinter` library, making it accessible to non-technical event staff. It integrates with Gmail's SMTP server for email delivery, uses OpenCV for real-time webcam QR scanning, and stores data in both CSV and Excel formats.

### 4.2 Function Reference

#### `send_confirmation_email(name, email, send_email)` — Lines 26–60

**Purpose**: Sends a plain-text confirmation email to a scanned participant.

**Flow**:
1. Reads SMTP credentials from environment variables (`EMAIL_USER`, `EMAIL_PASS`).
2. Reads custom subject from `email_subject_var` (a `tk.StringVar` — GUI widget).
3. Reads custom body from `email_body_var` (a `tk.Text` widget), defaulting to a hardcoded template if blank.
4. Replaces `{Name}` placeholder with the participant's actual name.
5. Connects to `smtp.gmail.com:587` with STARTTLS, authenticates, and sends.
6. Calls `log_email()` to record the outcome.

**Critical Detail**: This function reads from **live GUI widgets** from inside a **background thread**. This is a **tkinter thread-safety violation** — tkinter is not thread-safe, and accessing widget state from non-main threads can crash or produce corrupted reads.

---

#### `log_email(name, email, status)` — Lines 63–70

**Purpose**: Appends one row to `email_logscan.csv`.

**Logic**:
- Creates a single-row DataFrame.
- If the CSV doesn't exist yet, writes it with a header.
- Otherwise, appends without writing the header again.

**Flaw**: No file locking. If multiple emails complete simultaneously (multiple threads), they can interleave their `append` writes → corrupted CSV.

---

#### `scan_qr_code(main_sheet)` — Lines 73–130

The **core scanning engine**. Runs in a background thread.

**Flow**:
```
Open webcam (cv2.VideoCapture(0))
  └── Loop while scanning == True:
        ├── cap.read() → get frame
        ├── pyzbar.decode(frame) → find all barcodes
        │     └── For each barcode:
        │           ├── Decode bytes → unique_id string
        │           ├── Check against last_scanned set (dedup)
        │           ├── Lookup UniqueID in main_sheet DataFrame
        │           │     └── If found: extract Name, Email
        │           ├── Append to scanned_data list
        │           ├── Spawn thread: send_confirmation_email(...)
        │           └── Call update_table(scanned_data) [GUI UPDATE FROM THREAD]
        ├── cv2.imshow() → render frame
        └── cv2.waitKey(1) → check for 'q' keypress
  └── cap.release() + cv2.destroyAllWindows()
  └── If scanned_data: save_to_csv() + update_attendance()
```

**Key Implementation Details**:
- **Deduplication**: `last_scanned` is a `set` — once a `UniqueID` is scanned, it won't be processed again in the same session, preventing duplicate attendance records.
- **In-memory accumulation**: `scanned_data` is a list of dicts built in RAM during the session; it's only persisted when scanning stops.
- **No match handling**: If a scanned QR code's ID doesn't exist in `main_sheet`, it is silently ignored — no alert or log.

---

#### `update_table(scanned_data)` — Lines 139–144

Refreshes the `ttk.Treeview` widget with current scan data. Called from the scanning thread — **direct GUI mutation from a non-main thread**, which violates tkinter's threading rules.

---

#### `save_to_csv(scanned_data)` — Lines 146–149

Converts `scanned_data` list to a DataFrame and saves to `scanned_qr_data.csv`. Overwrites any previous session data (no append mode).

---

#### `update_attendance(main_sheet, scanned_data)` — Lines 151–166

**The most complex function.** Merges scan results with the master participant sheet.

**Pandas Operations**:
```python
merged_df = pd.merge(main_sheet, scanned_df, on='UniqueID', how='left')
merged_df['Attendance'] = merged_df['Timestamp'].notna().replace({True: 'Present', False: 'Absent'})
merged_df.to_excel('updated_attendance_sheet.xlsx', index=False)
```

- **Left join** on `UniqueID` ensures every original participant appears in the output.
- Participants with a non-null `Timestamp` (from scan data) → `'Present'`; others → `'Absent'`.
- Column collision risk: if `main_sheet` already has a `Name_x`/`Name_y` split due to duplicate column names after merge, this could produce messy output.

---

#### `load_main_sheet()` — Lines 184–194

Loads the user-selected `.xlsx` file with `pd.read_excel()`. Returns `None` on failure. No schema validation is performed — if required columns (`UniqueID`, `Name`, `Email`) are missing, the app will crash downstream with a `KeyError`.

---

#### `send_email(name, email, pdf_file, email_body, subject, attachments=[])` — Lines 40–83

**Purpose**: Constructs and sends a MIME multipart email with PDF attachment.

**Email Structure**:
```
MIMEMultipart
  ├── MIMEText (plain text body, with {name} substituted via .format())
  ├── MIMEBase (PDF ticket, base64-encoded)
  └── MIMEBase × N (any additional attachments chosen by user)
```

**Authentication**: Gmail SMTP with STARTTLS on port 587.

**Return Values**: `"Sent"` on success, `"Failed"` on exception. The exception is printed to stdout but **not re-raised** and **not shown in the GUI** — failed sends can go unnoticed except in the log.

**Mutable Default Argument Bug**:
```python
def send_email(name, email, pdf_file, email_body, subject, attachments=[]):
```
`attachments=[]` as a default argument is a classic Python pitfall — the same list object is shared across all calls where no attachment is passed. While it doesn't cause bugs here (the list is only read, not mutated), it is bad practice.

---

#### `send_personalized_tickets(file_path, email_body, subject, attachments)` — Lines 86–117

**Purpose**: Orchestrates the full ticket-generation-and-send pipeline for all CSV rows.

**Flow**:
```
pd.read_csv(file_path)
  └── Validate columns: [Name, Email, UniqueID]
  └── For each row:
        ├── Basic email validation (check for '@')
        ├── generate_ticket_pdf(name, unique_id) → pdf_file
        ├── send_email(...) → status
        ├── Append to email_log DataFrame
        ├── os.remove("qrcode.png")   ← temp cleanup
        └── os.remove(pdf_file)       ← temp cleanup
  └── email_log.to_csv("email_log.csv")
  └── Return (total_sent, total_failed)
```

**Performance**: This runs **synchronously** in a loop — for 500 participants, every ticket is generated and emailed one by one. There is no concurrency, batching, or rate limiting. Gmail SMTP has rate limits (~500 emails/day for standard accounts; sending in bulk can trigger account suspension).

**Email Validation**: Only checks `'@' in email` — this is an extremely weak check. `"not@valid"` or `"@"` would both pass.

---

#### `schedule_send()` and `delayed_send(delay)` — Lines 156–169

**Purpose**: Allows users to schedule the bulk email dispatch for a future time.

**Mechanism**: Parses a user-supplied datetime string, computes the delay in seconds, then starts a `threading.Thread` that calls `time.sleep(delay)` before invoking `send_tickets()`.

**Problem**: `time.sleep()` with a potentially large delay (hours) on a non-daemonized thread means:
- The thread holds open for the entire duration.
- Closing the main window doesn't cancel the scheduled job.
- No cancellation mechanism exists — once scheduled, it cannot be aborted from the GUI.

---

#### `preview_email()` — Lines 137–153

Opens a `Toplevel` window showing the rendered email with a sample name. Uses `.format_map()` for safe placeholder substitution. Catches `KeyError` for invalid placeholders.

## 7. Threading Model

The application uses Python's `threading.Thread` for two purposes:

### Thread 1 — QR Scanning Thread

```python
scan_thread = threading.Thread(target=scan_qr_code, args=(main_sheet,))
scan_thread.start()
```

- Runs the OpenCV capture loop.
- **Not daemonized** — if the main window closes while scanning, this thread may hang.
- Shares `scanning` (bool) with the main thread — the main thread sets `scanning = False` to signal termination.

### Thread 2 — Email Dispatch Threads (one per scan)

```python
threading.Thread(target=send_confirmation_email, args=(name, email, send_email)).start()
```

- A new thread is spawned **for each scanned QR code**.
- Also not daemonized.
- Accesses `email_subject_var` and `email_body_var` (tkinter widgets) from a non-main thread — **thread-safety violation**.

### Thread 3 — Scheduled Send Thread

```python
threading.Thread(target=delayed_send, args=(delay,)).start()
```

- Sleeps for the computed duration, then calls `send_tickets()`.
- Cannot be cancelled from the GUI.

### Thread Safety Summary

| Issue | Location | Risk |
|---|---|---|
| GUI widget reads from background thread | `send_confirmation_email()` | Crash / data corruption |
| `update_table()` called from scan thread | `scan_qr_code()` | Crash / visual glitch |
| Unsynchronized `scanning` flag | Both threads | Stale read possible |
| Concurrent CSV appends | `log_email()` | Corrupted log file |

## 10. Security Analysis

### What's Done Right

- **Environment variable credentials**: Email credentials are loaded from `.env` via `python-dotenv`, not hardcoded in source.
- **STARTTLS**: Connection to Gmail SMTP uses `server.starttls()` before authentication — credentials are sent over an encrypted channel.

### Vulnerabilities & Concerns

| Issue | Severity | Detail |
|---|---|---|
| `.env` file in repo root | High | `emailpass.env` exists in the repo. If accidentally committed to Git, credentials are exposed. The `.gitignore` file should explicitly exclude `*.env`. |
| No Gmail App Password enforcement | Medium | The README mentions plain password, which no longer works with Google's security policies since 2022. App Passwords or OAuth2 are required. |
| Weak email validation | Medium | Only checks for `@` presence. Invalid addresses will cause SMTP errors at runtime. |
| PDF written to CWD | Medium | Files named `{Name}_Event_Ticket.pdf` written to CWD — if two participants share a first name, the second ticket will overwrite the first. |
| `qrcode.png` race condition | High | `qrcode.png` is a shared temp filename used by all iterations in the loop. If parallelism were introduced, concurrent writes would corrupt it. |
| No input sanitization | Medium | `Name` from CSV is used in filename construction — names with `/`, `\`, or `:` would break `os.path` on certain OSes. |
| Email body from GUI in background thread | Medium | Reading tkinter widget state from a non-main thread is undefined behavior. |

## 11. Known Bugs & Edge Cases

### Bug 1 — Treeview Updated from Scan Thread

```python
# In scan_qr_code() — runs in a background thread:
update_table(scanned_data)  # Directly modifies tkinter widgets — UNSAFE
```

**Impact**: In CPython with GIL, this often "works" but is technically undefined. Under load, it can cause visual corruption or crashes.

**Fix**: Use `root.after(0, update_table, scanned_data)` to schedule the GUI update on the main thread.

---

### Bug 2 — Progress Bar Never Updates

```python
progress = ttk.Progressbar(root, length=300, mode='determinate')
```

The progress bar in `email_ticket_sender.py` is created but `progress['value']` is never set during the send loop. Users see no progress feedback during a bulk send.

---

### Bug 3 — Scheduled Send Cannot Be Cancelled

Once `schedule_send()` fires, a `time.sleep(delay)` thread is spawned with no handle stored. There is no UI element to cancel the scheduled job.

---

### Bug 4 — Column Name Collision After Merge

If `main_sheet` contains columns `Name_x`, `Email_x`, or `Timestamp`, the pandas merge will create `_x`/`_y` suffixed columns, potentially breaking the `Attendance` logic:

```python
merged_df['Attendance'] = merged_df['Timestamp'].notna()...
# Will fail with KeyError if column is now 'Timestamp_y'
```

### Bug 5 — Silent Drop of Unrecognized QR Codes

If an attendee presents a QR code whose `UniqueID` is not in `main_sheet`, the code is silently ignored:

```python
participant_data = main_sheet.loc[main_sheet['UniqueID'] == unique_id]
if not participant_data.empty:
    # ... process
# No else: no feedback, no log
```

**Impact**: Unknown or unauthorized QR codes produce zero feedback. An event organizer may not know someone attempted to scan an invalid ticket.

### Bug 6 — Duplicate PDF Filename Collision

```python
file_name = f"{name}_Event_Ticket.pdf"
```

If two participants share the same name (e.g., "John Smith"), the second PDF will overwrite the first before it is emailed.

### Edge Case — Camera Index Hardcoded

```python
cap = cv2.VideoCapture(0)
```

Camera index `0` is the default device. On systems with multiple cameras, this may select the wrong one. There is no UI to choose the camera.

## 12. Performance Considerations

### Email Ticket Sender

| Scenario | Performance Impact |
|---|---|
| 100 participants | ~5–15 seconds depending on network |
| 500 participants | ~30–90 seconds (sequential, no batching) |
| 1000 participants | Likely to hit Gmail 500/day rate limit |

The send loop is fully sequential: **generate PDF → send email → delete files → next row**. A thread pool with concurrent sends and PDF generation would offer a 3–5x speedup, but would require careful temp-file naming.

### Attendance Scanner

- **Frame processing**: `pyzbar.decode()` runs on every frame (~30fps). For a typical event, this is negligible CPU load.
- **Excel lookup**: `main_sheet.loc[main_sheet['UniqueID'] == unique_id]` is a linear scan of the entire DataFrame per QR code. For 10,000 participants, this is still milliseconds, but setting the DataFrame index to `UniqueID` would make it O(1):

```python
main_sheet = main_sheet.set_index('UniqueID')
# Then:
participant_data = main_sheet.loc[unique_id]  # O(1) hash lookup
```

## 14. Improvement Recommendations

### Priority 1 — Critical Fixes

1. **Fix Thread Safety**: Replace direct GUI calls from background threads with `root.after()`:
   ```python
   # Instead of: update_table(scanned_data)
   root.after(0, update_table, scanned_data)
   ```

2. **Set `daemon=True` on threads** so they terminate when the main window closes:
   ```python
   t = threading.Thread(target=scan_qr_code, args=(main_sheet,), daemon=True)
   ```

3. **Use `threading.Event` for scan control** instead of a bare boolean:
   ```python
   stop_event = threading.Event()

   # To stop: stop_event.set()
   ```

4. **Validate input schemas** before processing:
   ```python
   required = {'UniqueID', 'Name', 'Email'}
   if not required.issubset(main_sheet.columns):
       messagebox.showerror("Error", f"Missing columns: {required - set(main_sheet.columns)}")
       return None
   ```

   progress['maximum'] = len(data)
   progress['value'] = index + 1

7. **Index the DataFrame by `UniqueID`** for O(1) lookups.

8. **Add a send cancellation button** for the scheduled email job.

    file_name = f"{unique_id}_ticket.pdf"  # UniqueIDs are guaranteed unique
